# Standalone native integration design

Status: design proposal for review; no app, server, model or test described below has been implemented or run in this design session. Baseline: `d2ce1847cb2644252f7c4d069ef9e36142bb327b`. The next session implements this design with Luna (Max); this session ends after Astra design, Claude/Fable review and handoff. No commit or push is authorized by this document.

## 1. Purpose and decisions

Add runnable SwiftUI and Jetpack Compose verification apps in this repository, with a controllable Python standard-library HTTP server. Connect the existing managed session to actual HTTP, actual credential storage and displayed UI. The primary acceptance sequence is **refresh issued → Logout completed → old success or failure delivered → credential absence and logged-out UI preserved**. A subsequent explicit login may establish new credentials; an old completion must neither replace nor clear them.

This is a local demo using synthetic tokens, without authentication accounts, OAuth/OIDC, production endpoints or distribution. The existing synchronous and asynchronous libraries, public APIs, package platform floors, fixtures, negative controls, TLA+ gates and history checker remain authoritative and unchanged. New integration expectations are additive and independently authored; app output never generates its own expected output.

Chosen architecture: one FIFO command consumer owns each app's managed session, credential store and UI publication sequence. Network tasks execute outside this consumer and return immutable completion commands. Alternatives considered: placing storage inside the existing managed library would broaden its API and OS requirements; launching independent effect tasks after each managed result would permit a stale write or publication after Logout. A transactional database would not make the separate main-thread UI transaction atomic. The FIFO boundary is small enough to model and instrument without changing the library.

Only one app coordinator and one store namespace exist per process. Android owns them in `Application`; iOS owns them in the SwiftUI `App` composition root. Activity recreation/view recreation attaches to the same current view model; it does not construct a new session. No multiprocess component, app extension, background URLSession, WorkManager job or restored network task is included.

## 3. Observable behavior and commands

The app displays session state, signed-in account label (`demo-A`/`demo-B`), credential status (`absent`, version label, `unknown`), current request ID, last completed command, error and a redacted event log. Buttons: `Login A`, `Login B`, `Expire token`, `Logout`, `Retry cleanup`, and a demo-only scenario panel for hold/release/replay/cancel. Authenticated content is visible in `SignedIn` and `Refreshing`; `Booting`, `SignedOut`, `SigningOut` and `FaultLocked` expose no authenticated content. Raw token values never appear in UI/logs/artifacts.

The Login action uses a known synthetic seed credential (`demo-A-v0` or `demo-B-v0`); no asynchronous login flow is modeled. It is admitted only when health is Ready and the managed state is Unauthenticated with verified absent storage. Login while authenticated/refreshing returns `RejectedBusy` without calling the managed library. Account replacement is an explicit completed Logout followed by Login. This restriction avoids inventing credential semantics for the existing Authenticated × LoginSucceeded `ClearCredentials` row; the library row remains covered by old gates.

| Command | Effect and completion condition |
|---|---|
| Bootstrap | Verify-delete any previous demo credential, create a fresh managed owner, publish SignedOut; errors publish FaultLocked |
| Login(account) | Store seed credential + readback, handle `.loginSucceeded`, assert Authenticated, publish SignedIn; acknowledge only after publish |
| Expire | Handle `.tokenExpired`; for its request effect create one retained slot, launch HTTP without awaiting response, publish Refreshing; repeated Expire launches nothing |
| Logout | Publish SigningOut, invalidate current slot, handle `.logout`, execute ClearCredentials, additionally ensure-delete for an already unauthenticated state, verify absence, publish SignedOut, then acknowledge Completed |
| Deliver(slot, outcome) | Reduce through the original request object; eligible success replaces credential, eligible failure clears it; stale/duplicate/foreign completion preserves credentials/authProjection and publishes completion metadata |
| CancelRefresh | Same logical invalidation/clear contract as Logout, then best-effort physical cancellation; acknowledge cleanup independently of network termination |
| Observe | Queue behind earlier commands, return coherent managed snapshot, actual store readback and current published model revision |
| RetryCleanup | In FaultLocked, retry delete/readback, create fresh managed owner, invalidate all slots, publish SignedOut; reject Login until success |

`Completed` is not emitted when deletion/readback/publication fails. `FaultLocked(error)` is a completed *failure* result, not successful Logout. Timeouts/missing results are NOT_RUN/INFRA_FAILURE in the evaluator, never implicit success. All app command/epoch-label/audit/revision counters use checked signed64 arithmetic; inability to allocate the next value triggers terminal `CounterExhausted` process abort with no successful receipt and no attempted new revision/publication. This deliberately rare fail-stop path cannot wrap/reuse IDs or require a FaultLocked UI revision which no longer exists; its missing operations make the test run non-PASS. The next launch follows bootstrap cleanup. The separate library allocator's `RequestIdExhausted` remains a recoverable unchanged-snapshot rejection and does not abort the process.

## 4. One transaction at a time, including across await

### 4.1 Runtime ownership

`SessionCoordinator` exclusively owns a `ManagedAsyncSession`, `CredentialStore`, active refresh slot, process-local epoch, mailbox and command sequence. No UI or transport callback calls managed methods or the store directly; the evaluator's frozen read-only probe is the explicit test exception described below. The store has no timer, deferred write or callback. Every mutation/delivery command runs to its publication acknowledgement before the next is dequeued; Observe returns the current coherent observation without publication.

Swift uses an actor mailbox with a single `draining` flag. `submit` appends a command plus continuation and starts the drain only if it was stopped. During `await session.handle(...)` or `await publisher.publish(...)`, actor reentry may append commands but **must never execute a second command**, reset the draining flag, publish or access persistence. Only the existing drain mutates transaction state. The drain task is coordinator-owned; cancellation of a view task awaiting `submit` does not cancel an accepted Logout. Every continuation completes exactly once. The managed actor itself retains its existing no-internal-await atomic method.

Android uses one `Executors.newSingleThreadExecutor` for the coordinator. A command performs managed calls and synchronous store I/O there; UI publication is posted to the main looper with an acknowledgement which the worker awaits before processing the next command. The main thread never blocks waiting for the worker; the public API returns `CompletableFuture<CommandReceipt>`. HTTP runs on a different bounded executor. No callback executes a command inline even when a future is already complete. Shutdown belongs to application/test teardown, not Activity destruction.

UI publisher assigns one immutable `DemoViewState` on MainActor/main looper and then acknowledges. It enforces increasing revision, uses no unstructured delayed publication, never reads storage, and holds no credential values. If main-thread acknowledgement does not arrive, the command cannot be reported complete. Assignment acknowledgement does not prove a rendered frame; UI tests separately wait for accessible view state matching the acknowledged revision.

Command IDs and `commandEnqueued` records are assigned atomically with actual enqueue. FIFO means that recorded order, not source order between independently scheduled caller Tasks/threads. Swift's actor protects enqueue; Android uses a short enqueue lock around ID assignment and executor submission. The lock does no I/O and is released before command execution. A test may wait for an enqueue record while a prior consumer is paused, then submit another command to establish the desired order.

### 4.2 Atomicity boundary and linearization

There is no cross-system atomic transaction spanning Keychain/file, managed actor and pixels. Internal intermediate states exist. The contract is serializable **completed app commands** and safe publication: only after persistence verification may authenticated UI publish; no later command begins until prior publication is acknowledged. External direct store access and raw managed state access are outside the app API.

The managed operation linearizes inside its existing actor/monitor. App command order linearizes at dequeue for successful sequential semantics; its externally visible commit is its final publication acknowledgement. The record includes both points. Logout's invalidation point is the current-slot clear at the start of its transaction; its success boundary is verified credential absence plus SignedOut publication acknowledgement. An earlier success can write before Logout starts, but Logout cannot complete ahead of that write. A later old success cannot become eligible. A subsequent Login cannot race an earlier delete because it cannot start until the Logout transaction ends.

Always execute ordered `ClearCredentials` effects within the transaction that produced them; never enqueue the effect as later independent work. A failure during a success write triggers same-transaction fault cleanup and hides authentication before allowing the next command. Network task completion, JSON decoding and arrival logs do not confer commit authority.

### 4.3 Exact response binding

The library event/effect carries no credential payload. The adapter retains the emitted **actual opaque object** in an immutable `RefreshSlot`:

```text
RefreshSlot = reference identity {
  request: original RefreshRequest,
  processEpoch: retained Epoch reference,
  issuanceCommandId, wireTag, accountLabel, seedCredentialVersion
}
Completion = { slot: original RefreshSlot, outcome: Success(Credential) | Failure(code) }
```

`wireTag` is the diagnostic string `<processInstanceId>:refresh:<issuanceCommandId>`, unique in a run but not an owner capability. HTTP request IDs are decimal strings and may repeat under a new managed owner. Neither response JSON nor persisted data can construct/restore a RefreshRequest. The URLSession closure/network executor closure captures the slot; it validates wire correlation and enqueues `Completion(slot, parsedOutcome)`. No lookup of authority by numeric ID alone; no deserialization of owner identity. A new owner's allocator starts at its normal initial value; carrying the previous owner's next ID forward is intentionally rejected because the existing contract permits equal numbers under distinct owners and safety depends on retained object identity, not run-wide numeric uniqueness.

At the beginning of Deliver, capture the managed pre-snapshot. Eligibility is the conjunction of `health == Ready`, `slot === activeSlot`, retained epoch identity match, `pre.state == Refreshing`, and `pre.pendingRequestId == slot.request.requestId`. Submit the corresponding managed response with **that same request object**, including for stale deliveries retained by the harness. A successful credential commit additionally requires no rejection and post-state Authenticated with no pending ID. Eligible failure requires Unauthenticated, no pending ID and ClearCredentials. Unexpected result shapes cause FaultLocked; do not assume `rejection == nil` alone means success, because stale responses are no-ops with nil rejection.

Bootstrap creates an epoch identity. Logout, CancelRefresh, fault entry and RetryCleanup replace that retained identity and clear the active slot before any later eligible completion; Login uses the current epoch. Epoch identity is an in-memory object, with a checked numeric label solely for logs/model projection. It is never serialized as authority.

The policy of forwarding stale/foreign deliveries to the managed layer is retained. Source inspection at the baseline confirms the Swift `AsyncSession.handle` response guard and Kotlin `AsyncSession.handle` early return preserve the full triple for either stale response in Unauthenticated, Authenticated and Refreshing. The async JSON rows use `activeResponse`; `verification.async_contract.step` only activates it for Refreshing with equal pending ID, and `policy_errors` independently requires stale full-state preservation. Managed owner checks reject foreign requests before numeric reduction. This is source evidence, not a newly executed test. Before freeze add evaluator regression cases for both response kinds in each state and a same-number foreign-owner case. The slot/epoch checks are additional defenses alongside these managed guards; removing one redundant guard alone is not guaranteed to reveal a fault.

Consume `activeSlot` exactly once before committing an eligible completion. Stale/duplicate completion compares the full managed pre/post snapshot and requires no effects; it records `IgnoredStale` without credential mutation or changed auth projection. Foreign rejection records `IgnoredForeign` with the same preservation. Every mutation/delivery command, including ignored or rejected outcomes, publishes a final metadata revision containing `lastCompletedCommandId` and `lastCommandStatus`, then acknowledges its receipt. Accessibility labels expose both, so the UI harness can wait for processing without live-reading an audit file. `authProjection(view) = (phase, account, credentialVersion, pendingRequestId)` remains unchanged on ignored delivery; revision/status/last-command metadata may change. Observe is read-only and returns the current model without publishing a new revision. In FaultLocked, delivery is discarded without managed calls and may update only completion metadata. Payload credentials remain local to the completion and are released after the command. Bounded replay retention is test infrastructure, never a persisted refresh capability.

## 5. Persistence, errors and lifecycle

### 5.1 Debug control plane and runtime observations

The test API is app-local `DebugScenarioControl`, using the exact interfaces/types in the companion plan: `arm(point,target)`, `awaitArrival(point,timeoutMillis)`, `release(point)`, `replayLastCompletion()`, `injectStoreFault(kind)`, `probeStore()`, and `snapshot()`. It has its own short lock/signals and a diagnostic `controlRevision`, separate from auth `DemoViewState.revision`. Arm/release/arrival-wait/fault-configuration/probe actions **never enqueue behind the paused SessionCoordinator transaction**. No control lock is held across an await, UI dispatch or store call. The control plane cannot mutate managed auth state, credentials or the auth projection; fault configuration only changes a thread-safe wrapper's next matching I/O behavior. Replay schedules the retained captured completion through ordinary Deliver, never writes it directly. The frozen probe is read-only and allowed only when the consumer reports store I/O idle at a quiescent or declared paused boundary.

Hook points are `beforeBootstrapClear`, `afterManaged`, `beforeStore`, `beforePublish`, `afterPublishAck`, `afterLogoutReceipt`, `ingressHeld`, `beforeDeferredControlClear`. A hook has one arm/arrival/release cycle; duplicate arm/release, release-before-arrival or a missing replay completion returns an explicit control error. No command receipt is forged by a control acknowledgement. Bootstrap's hook executes before the first deletion/readback with Booting UI; launch-time arms are installed before Bootstrap is submitted.

Control snapshot fields are `version`, `processInstanceId`, `launchOrdinal`, `controlRevision`, `lastActionId`, `lastActionStatus`, `lastEnqueuedCommandRef`, `lastProcessedCommandRef`, `storeIoActive`, `hooks` (point/phase/target/arrivalCommandRef), and `lastProbe` (probeId/observation). Fields contain only redacted diagnostic data. Enqueue/barrier callbacks update this independent snapshot synchronously under its short lock; main-thread rendering of the diagnostic snapshot occurs separately, with monotonically increasing controlRevision. It must remain readable while the auth consumer is suspended. `awaitArrival` waits on the control plane's own signal, not the auth mailbox; timeout is an explicit test failure.

iOS XCUITest drives a Debug-only panel with accessibility IDs `hook-target-<bootstrap|nextCommand|nextDelivery>`, `hook-arm-<point>`, `hook-release-<point>`, `hook-state-<point>`, `replay-last`, `fault-set-<kind>`, `probe-store`, `store-probe-result`, `control-status-json`, and `last-enqueued-command-id`; the existing auth/status labels remain separate. `hook-state` exposes phase plus arrival command reference; `control-status-json` exposes the complete bounded snapshot so the test can wait for enqueue or arrival without live-reading files. Target buttons select the next arm's target; initial bootstrap target is set by launch arguments. Android instrumentation calls the same control API directly through `DebugDemoApplication.debugControl` and may read the same panel labels. Its frozen `DemoTestRunner` injects parsed startup configuration in `callApplicationOnCreate` before delegating to Application.onCreate, so a launch-time hook cannot miss Bootstrap. Release composition has neither this runner nor the Debug application subclass.

Startup arguments are explicit pairs: iOS `--scenario-id`, `--run-id`, `--process-instance-id`, `--launch-ordinal`, `--base-url`, `--arm <point>`, `--arm-target <bootstrap|nextCommand|nextDelivery>`, `--store-fault <kind>`; Android instrumentation arguments use camelCase keys `scenarioId`, `runId`, `processInstanceId`, `launchOrdinal`, `baseUrl`, `armPoint`, `armTarget`, `storeFault`. Launch arms/faults are parsed before coordinator Bootstrap. No token or control key is an argument. For non-test manual startup the composition root generates its own diagnostic process ID; it cannot restore a previous capability.

### 5.2 Storage and process lifecycle

iOS stores one JSON blob in a generic-password Keychain item: service `native-contract-demo.credentials`, account `current`, accessibility `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, synchronization disabled. Replacement is an update, falling back to add only for item-not-found, followed by readback of exact version/account/value in memory. Deletion accepts success/item-not-found and verifies absence with `SecItemCopyMatching`; all other OSStatus values are failures. No blanket deletion of other Keychain items. Keychain accessibility errors while locked enter FaultLocked. [Keychain accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility).

Android stores a versioned synthetic credential JSON blob in `context.noBackupFilesDir/demo-session/credential.json` through `AtomicFile.startWrite/finishWrite/failWrite`, then reads it back. The single coordinator is also the file lock. Deletion uses `AtomicFile.delete` and verifies absence through the abstraction, including recovery sidecar handling; a silent failed delete is an error. `android:allowBackup="false"`; storage is private to the app. Keystore encryption is deferred: these values are explicitly nonsecret demo fixtures, and testing hardware-backed key lifecycle adds no evidence about stale response ordering. Real credentials would require a separate security design. `AtomicFile` does not replace synchronization. [AtomicFile](https://developer.android.com/reference/android/util/AtomicFile), [app-private files](https://developer.android.com/training/data-storage/app-specific).

`CredentialStore` methods are synchronous and may throw; no `SharedPreferences.apply`, asynchronous DataStore update, fire-and-forget SecItem operation or delayed retry. `replaceVerified` and `clearVerified` include readback. Inject failures both before mutation and after mutation/before verification. A failure means the physical store may be unknown; report `credentialStatus=unknown`, never `absent` without readback. In FaultLocked the coordinator invalidates slots, handles managed Logout when possible, best-effort clears storage, publishes a locked signed-out view, rejects Login/Expire and permits only Observe/Logout/RetryCleanup. A failed UI publication prevents a successful receipt and the harness times out; there is no claim that missing UI acknowledgement implies UI changed.

An evaluator-owned, frozen `StorageProbe` is a narrowly scoped read-only test exception to the sole-store-access rule, invoked after a quiescent receipt/Observe or at an explicitly paused transaction barrier with no store operation in progress. iOS probe has its own `SecItemCopyMatching` query and strict decoder, never calls candidate `KeychainCredentialStore` or uses cached UI values. Android's authoritative probe is host-controller `adb exec-out run-as <package> cat <owned-file>` plus exact owned base/sidecar existence observations; app-local probing is supplementary. The host interprets absent base/sidecars versus read/permission/parse error, not every failed `cat` as absence. Probes cannot mutate storage or race store I/O. Raw credential bytes are decoded only in memory; emit account/version/absence/error and optional SHA-256 of the synthetic blob, never token values. Controller capture must redact this probe subprocess stdout before persistent logs; capture only command/exit metadata and redacted result. Control keys likewise never enter artifacts, command arguments or screenshots.

Debug test Keychain service is `native-contract-demo.credentials.test.<attemptId>.<scenarioId>`; Android test files use `noBackupFilesDir/demo-session/test-<attemptId>/<scenarioId>/`. That namespace persists across a scenario's process-restart tests and is never changed mid-run. Cleanup deletes only the run's namespace. Normal manual runs use the fixed demo namespace above. Independent store probes immediately after each Logout receipt are required before any later Login/RetryCleanup/release step in APP-02/03/04/05/10/11 and corresponding controls.

Bootstrap always attempts verified deletion **before enabling Login or displaying authenticated content**. It never restores a saved token into a logged-in session. Each process creates a fresh owner/epoch; HTTP uses foreground ephemeral tasks. Process death can occur between any two operations: the next launch shows Booting/FaultLocked until cleanup succeeds. No transactional power-loss durability, credential erasure from physical media, background revocation or crash recovery preserving login is claimed. Relaunch after a stored credential and after a Logout is a required smoke test. Systematic kill-at-every-instruction testing and resumable authenticated sessions are future work.

Configuration changes on Android and SwiftUI view reattachment preserve coordinator ownership. No old UI observer may issue a deferred auth publication after a new observer attaches; observers read the current monotonically revisioned model. Do not persist `DemoViewState` using saved-state mechanisms.

Android automation builds/installs the app and test APK once per candidate stage, then the controller runs one `adb ... shell am instrument -w ...` invocation per declared scenario launch using argv arrays. APP-12's p1 saves the credential (or completes Logout for its second variant), writes a checkpoint/end marker and exports redacted evidence without clearing storage in teardown. After instrumentation exits, the controller explicitly `am force-stop`s the target and confirms `pidof` is empty; instrumentation completion alone is not evidence of process death. It then invokes p2 with the same scenario storage namespace, new launchOrdinal/processInstanceId and a launch-armed `beforeBootstrapClear`. The instrumentation worker emits an arrival status and waits for the server's process-scoped `bootstrapStoreProbed` checkpoint. While p2 is paused in Booting, the host probe observes persisted physical state and posts that checkpoint; the instrumentation worker then calls direct `release(beforeBootstrapClear)` and waits for Bootstrap cleanup. Final probe/UI must be Absent/SignedOut. Do not run `pm clear`, reinstall APKs or delete the credential namespace between p1 and p2. Process termination/checkpoint ordering is controller evidence, distinct from native command completion.

## 6. Formal integration contract

Add an independently authored finite integration transition system in `integration/model.py`, consuming the existing JSON oracle for managed steps and explicitly modeling the additional adapter/store/UI steps. It does not change `contract/specification.json`. Freeze `integration/contract.json`, invariants and scenario inventory before app candidate implementation.

Abstract state:

```text
S = (health, managed(state,pending,next), epoch, activeSlot,
     credential, ui, revision, mailbox, executing, pc,
     heldCompletions, receipts, lastCompletedLogout, postLogoutLogin)
health ∈ {Booting, Ready, FaultLocked}
credential ∈ {Absent, A0, A1, B0, B1, Unknown}
ui ∈ {Booting, SignedOut, SigningOut, SignedInA, SignedInB,
      RefreshingA, RefreshingB, FaultLocked}
pc ∈ {Idle, Reduced, StorePending, StoreVerified, PublishPending, Ack}
```

Model each command's phases as separate transitions, allowing arrivals/queued commands at every phase; the good model permits only one executing command. Environment actions enqueue Login/Expire/Logout, deliver success/failure/duplicate, report network cancellation, fail store calls, acknowledge UI, and restart. Restart clears volatile state and begins Bootstrap while preserving the modeled physical credential. Eligibility uses symbolic slot/epoch identity, not numeric equality alone. Ignore stuttering arrivals when checking commit invariants.

Named safety properties:

| ID | Predicate/obligation |
|---|---|
| I1 SingleConsumer | At most one command executes; next dequeue occurs only after current terminal receipt or FaultLocked publication |
| I2 CredentialAuthority | Every credential replacement is attributable to an admitted Login or an eligible successful current-slot completion, and its store phase precedes its auth publication |
| I3 NoResurrection | After a successful Logout receipt, while no later admitted Login has committed, credential is Absent and UI has no authenticated content at every subsequent stable boundary; old responses create no store write or promotion to an authenticated authProjection even at intermediate steps; SignedOut completion-metadata updates are permitted |
| I4 NewLoginIsolation | A completion or deferred effect from a revoked epoch/slot/prior Logout transaction cannot change the new account credential or auth projection, on success or failure |
| I5 ClearBeforeReceipt | Successful Logout receipt implies managed Unauthenticated/pending nil, verified absent credential and SignedOut acknowledged at that command's revision |
| I6 PublishAuthority | SignedIn/Refreshing publication requires Ready and the verified currently installed credential, including matching account/version; metadata-only updates preserve authProjection; revisions strictly increase within a process; a prior publication cannot occur after a later receipt in that process |
| I7 AtMostOnce | Each slot authorizes at most one completion commit; duplicate/stale/foreign paths preserve full managed snapshot, credentials and auth projection |
| I8 FaultClosed | FaultLocked prohibits authenticated publication and new Login/Expire; unknown/deletion failure never yields successful Logout |
| I9 BootstrapClosed | A fresh process cannot publish authentication from a persisted old credential; Ready begins only after successful cleanup |

`I6` is a publication-time property, not an assertion that old pixels instantaneously disappear at the start of every store operation. During Logout, SigningOut publication is acknowledged before deletion. During initial Login, SignedOut remains until store and managed work finish. During refresh credential replacement, an existing same-account auth screen may remain visible until next publication. Stable Observe and receipts are the complete observation boundary.

Finite bounds are explicit in the model report: two account labels, two managed-owner identities, three epoch identities (allowing Bootstrap → fault revocation → RetryCleanup), two issued request IDs per owner, up to two queued commands, one current and one retained old slot, at most one replay per slot, success/failure/cancellation, store success/fail-before/fail-after outcomes, at most six dequeued commands and twelve UI publications. Every component is finite: retain only bounded ghost summaries for receipts/commit bits; BFS predecessor/witness traces are metadata outside hashed states. Bound exhaustion disables further generation and permits terminal stuttering; it does not wrap values and is not the native counter-overflow policy. Observe is a read-only external projection/stutter for this model and does not consume its command bound. Bootstrap/Login A/Expire/Logout/Login B/Deliver old fit the six-command bound. Restart consumes the next Bootstrap command and requires unused bounded owner/epoch identities.

Non-vacuity coverage is required: the good model must exhibit canonical APP-02, APP-03, APP-04 and APP-05 paths, a duplicate-delivery path, a queued Logout during a paused store/publication path, a fault/cleanup path, and a restart with persisted credential followed by successful bootstrap cleanup, all within the declared bounds. The combined fault → RetryCleanup → Login B → old delivery path is not claimed under the six-command bound; exercise it in native integration tests with a separately frozen inventory. Missing required model reachability is INCONCLUSIVE, not invariant PASS. Record witness traces and chosen bounds. Exhaustive reachability is only over this finite instantiation; no fairness or unbounded liveness claim. Native max signed64 allocator coverage remains in existing gates. Keep independent model rules for adapter behavior; use `verification.async_contract.step` only for the managed triple transition, preserving an explicit relation to its returned effects/rejection.

Model negative controls must produce named counterexamples: replace the entire success predicate with `admittedSuccess := outcome is Success`, bypassing both eligibility and managed acceptance → I2/I3/I4; allow second consumer across store/publication wait → I1/I3; execute a duplicate deferred clear from prior Logout after Login B → I4; publish success without store verification → I6; treat failed clear as success → I5/I8. Removing only current-slot guard is an optional redundancy experiment, not an acceptance control: the remaining pending/managed-result/owner guards can still prevent a commit. Infrastructure errors and search-limit exhaustion are not detection. The finite model and observed app traces are complementary evidence, not an arbitrary native refinement proof.

## 7. Local HTTP server and wire format

Automation runs `python3 -m integration.server --bind 127.0.0.1 --port 0 --output <fresh-dir>`. After binding, atomically write `server-ready.json` with version/bindAddress/actual port/PID; the controller health-checks that port and injects BaseURL into the app. Each platform run owns a separate server/output namespace, preventing local parallel port collisions. Manual use may explicitly request port 8765. Use `ThreadingHTTPServer`, explicit request-size limit 16 KiB, maximum 16 runs and 8 pending requests/run, a lock plus per-request condition, and a 60-second hold deadline. Lock protects control state only; never hold it during socket I/O. Each run has a fresh ID; request tags are unique within it. Duplicate JSON keys, unknown fields, invalid IDs and oversized bodies reject with 400/413. Timeouts terminate a request and mark the scenario INFRA_FAILURE if its expected barrier was not reached.

Two planes share the local process: `/v1/refresh` data requests and `/control/...` test controls. The controller, or a debug scenario panel on the device, owns controls. The control plane contains no secrets; localhost is default. Physical-device mode requires explicit `--bind <LAN-IP>` plus a per-run randomly generated control key sent in `X-Demo-Control-Key`; do not bind all interfaces by default. App endpoints are restricted by configuration to loopback, emulator host alias or explicitly supplied private LAN address. No redirects or endpoints embedded in response bodies are followed. This is a trusted local test network, not a hardened internet service.

Wire fields use exact names and version 1; decimal IDs are strings to preserve signed64. Credential strings must match `demo-[AB]-v[0-9]+` and length ≤64. Fields account/version must agree with the synthetic value. A response must match captured `runId` and `requestTag`, but only the captured slot carries authority.

```json
POST /control/runs
{"version":1,"attemptId":"attempt-01","scenarioId":"APP-02","platform":"ios"}
200 {"version":1,"runId":"run-opaque","controlKey":"local-only"}

POST /v1/refresh
{"version":1,"runId":"run-opaque","requestTag":"attempt-01/APP-02/p1:refresh:3","requestId":"1","account":"A","refreshToken":"demo-A-v0"}

GET /control/runs/run-opaque/pending
200 {"version":1,"runId":"run-opaque","pending":[{"requestTag":"attempt-01/APP-02/p1:refresh:3","requestId":"1","status":"held"}]}

POST /control/runs/run-opaque/release
{"version":1,"requestTag":"attempt-01/APP-02/p1:refresh:3","outcome":"success","credentialVersion":1}
200 {"version":1,"requestTag":"attempt-01/APP-02/p1:refresh:3","status":"releaseAccepted"}

200 response to held /v1/refresh
{"version":1,"runId":"run-opaque","requestTag":"attempt-01/APP-02/p1:refresh:3","outcome":"success","credential":{"account":"A","version":1,"accessToken":"demo-A-v1","refreshToken":"demo-A-v1"}}

POST /control/runs/run-opaque/release
{"version":1,"requestTag":"attempt-01/APP-02/p1:refresh:3","outcome":"failure","failure":"rejected"}
401 response to held /v1/refresh
{"version":1,"runId":"run-opaque","requestTag":"attempt-01/APP-02/p1:refresh:3","outcome":"failure","failure":"rejected"}
```

Success release computes credentials from the original held request account; the controller cannot silently change it. Alternative release outcomes are `http500` (500 with canonical failure `server`), `malformed` (200 with fixed invalid JSON bytes), and `disconnect` (close socket before response). A release is single-use; releasing an unknown tag or a second release is 409. `DELETE /control/runs/{runId}` aborts held requests and deletes only that run. `GET /control/runs/{runId}/events` returns ordered server events with redacted body digest, requestTag, received/release/written/disconnected stages. `GET /health` returns version/ready without keys.

The frozen harness also uses a bounded metadata checkpoint bridge for cross-process observations: authenticated control `POST /control/runs/{runId}/checkpoints` accepts exactly `{version:1,processInstanceId,name:"bootstrapStoreProbed"}`; native test `GET /v1/checkpoints?runId=...&processInstanceId=...&name=bootstrapStoreProbed` returns `{version:1,ready:boolean}` without a control key. General independent-probe checkpoints use `storeProbe.<frozenStepId>`; only names declared in that scenario/control inventory are accepted, with at most 32 checkpoint entries per run. After a receipt/safe hook arrival, instrumentation reports a probe-request status and waits on its declared checkpoint before issuing another auth action or releasing the hook. This protocol also prevents APP-02/04/10 and control probes from racing a subsequent Login/clear. Only the controller posts ready after saving a redacted probe result.

Run creation's `attemptId` and scenario inventory determine allowed process IDs `<attemptId>/<scenarioId>/p<ordinal>`; ordinary scenarios allow ordinal 1, APP-12 declares ordinals 1 and 2. attemptId/scenarioId must be nonempty ASCII alphanumeric/hyphen/underscore labels of at most 64 characters. Query values are URL-encoded; unknown names/processes reject, duplicate POST is idempotent, and run teardown clears checkpoints. This is diagnostic test coordination, never refresh authority. Instrumentation polls with its remaining stage deadline and directly releases the hook or proceeds after `ready=true`. Server records checkpoint publication and native trace records release/progression, establishing probe-before-clear without a write into app credential storage or a blocked auth-mailbox command.

Delay is a server hold/release barrier, not a sleep duration. The controller waits for `held` before Logout; waits for the app's successful Logout receipt before releasing. `releaseAccepted` and `written` alone do not establish app delivery; require the app's `transportReceived` and `completionProcessed` events. There is one HTTP response per request. **Duplicate delivery is modeled explicitly in the app's demo ingress adapter** by replaying the same captured completion/slot once after a real HTTP response; never claim HTTP delivered multiple responses. Hold-at-ingress, replay and fault injection are enabled only in Debug and recorded as test seams.

Platform transport defaults: connect timeout 10s, total/read response budget 75s, server hold 60s. Actual deadline values and timeout errors appear in evidence. HTTP 401/500, invalid JSON, wrong echo/account/token shape, disconnect and timeout become `Failure(code)` tied to the captured slot. No retry. `URLSessionTask.cancel` and `HttpURLConnection.disconnect` are best effort. A callback after cancellation still passes through the same coordinator eligibility check. The main post-Logout success/failure scenarios set `cancelOnLogout=false` so physical cancellation cannot hide a bad commit path.

## 8. Frozen scenarios and evidence

`integration/scenarios.json` independently declares exact scenario IDs, commands, barriers, injected outcomes and required observations. `integration/control-scenarios.json` separately fixes complete mutation-control inventories before freeze. Runners consume them; they may not drop failed operations or invent token references. One run per scenario/platform, fresh app coordinator/store namespace reset verified at start. Native trace records have version/runId/scenarioId/platform/build hash, process namespace, sequence, command ID, event kind, command dequeued/completed, managed pre/result, issuance reference, store attempted/verified observation, UI published/ack revision and outcome. Credentials are represented by account/version labels; no token values. Server and device monotonic clocks are not compared; explicit requestTag and controller acknowledgements establish cross-process order.

Process namespace is exact: controller assigns positive `launchOrdinal` and opaque diagnostic `processInstanceId = <attemptId>/<scenarioId>/p<launchOrdinal>` in launch arguments. Each event carries `processInstanceId`, `launchOrdinal`, `localSequence` (strictly increasing within that process); command references are `{processInstanceId,id}` and UI observations are `{processInstanceId,revision,...}`. Command IDs and revisions may restart at 1 under a different processInstanceId; they are never compared numerically across launches. Controller launch/termination acknowledgements connect the pre/post-launch histories, retaining a scenario-wide controller sequence. Export paths are `<scenarioId>/p<launchOrdinal>/...`, so relaunch never overwrites prelaunch evidence. Reusing a processInstanceId for another launched process is INVALID_HISTORY. The storage namespace is scenario-scoped and survives these launches; owner/epoch references do not. `processInstanceId` is evidence routing, not authority to restore a slot. Old-process HTTP requests may disconnect; no old native completion is fabricated after relaunch.

Trace completeness requires start/end markers, frozen command inventory, all required barriers, complete receipts and final independent store probe + rendered UI observation. Old callback processing after Logout must be present, not inferred from elapsed time. Wait for terminal receipt identity/status availability before comparing expected status; a wrong status/value must be recorded as an observation, not turn into an endless expected-label wait. Missing/malformed history is INVALID_HISTORY; absent device/server/artifact is NOT_RUN/INFRA_FAILURE; bounds exceeded are INCONCLUSIVE. Semantic failure requires a complete well-formed inventory; never move invariant classification ahead of completeness to rescue an incomplete mutant. A trace must preserve managed oracle behavior and integration invariants. Device-specific arbitrary timings are checked separately, not required to match between platforms.

| ID | Required sequence and expected result |
|---|---|
| APP-01 | Login A → Expire held → release success → store A1, SignedIn A; one request/one commit |
| APP-02 | Login A → Expire held → completed Logout → release success → processed stale; store absent/SignedOut, zero post-Logout writes; cancellation disabled |
| APP-03 | Same as APP-02 with delayed 401 failure; no delete or auth UI mutation attributable to stale completion |
| APP-04 | Old A request → Logout complete → Login B → release A success; B0 and SignedIn B preserved |
| APP-05 | Same as APP-04 with old A failure; B credentials must not be deleted |
| APP-06 | Current success → replay same captured completion; no second store mutation, pending stays nil |
| APP-07 | Expire twice while held; single HTTP request; success then fresh Expire issues a distinct ID |
| APP-08 | CancelRefresh while held → cleanup complete → attempt response/replay delivery; no resurrection; report actual transport cancellation separately |
| APP-09 | Store replacement fail-before and fail-after variants; no successful login/refresh receipt; FaultLocked, no auth publication after fault |
| APP-10 | Clear fail-before and verification-fail variants; Logout not Completed, FaultLocked; later RetryCleanup permits Login only after verified absence |
| APP-10-RECOVER-OLD | Hold A refresh → failed Logout/probe → RetryCleanup → Login B → release old response; ignored foreign/stale completion metadata and B preserved; native coverage beyond the six-command model |
| APP-11 | Pause store/publication transaction at test barrier, enqueue Logout then Login B; prove queued commands cannot overtake prior write/clear/publication; run both store and UI pause variants |
| APP-12-SAVED / APP-12-LOGGED-OUT | Separate concrete restart inventories: p1 saves A or completes Logout; p2 has a new process namespace, observes physical state before bootstrap clear, and ends Absent/SignedOut |
| APP-13 | Server 500/malformed/disconnect and wrong echo validation; current request fails closed, old request cannot clear a later Login |
| APP-14 | Account view/Activity recreation during held refresh; original coordinator/slot retained, no duplicate HTTP or old UI publication |

APP-02/03 are required as real HTTP + real store + rendered UI flows on both iOS Simulator and Android emulator. APP-04/05 and normal APP-01 run there too. All scenarios run on the integration adapters; OS storage failure injection uses a wrapper around the real store and is identified as injected. Actual OS-storage readback and UI observation remain separate from coordinator-generated audit events. At least APP-01/02/03 manual smoke on available physical devices is documented separately; absent physical devices do not masquerade as tested devices and do not block simulator/emulator acceptance.

A small evaluator-owned `unsafe-unconditional-commit` fixture uses the real library to generate a valid stale no-op, then deliberately writes/publishes its old payload. It must fail APP-02 and APP-04 semantically. The baseline repository has no application; inability to build a nonexistent old app is NOT_RUN, **not old-native semantic RED**. Preserve the existing old-native v4 RED through the original clean reproduction protocol and use the unsafe adapter fixture for the new integration RED.

Native candidate mutation controls apply only to isolated source copies after successful build. Freeze exact anchors and complete bounded inventories: `CTRL-N1-LOGOUT` and `CTRL-N1-NEW-LOGIN` end after old-success receipt, independent store probe and rendered UI observation (I2/I3/I4); `CTRL-N2-LATE-CLEAR` performs a real initial clear/Logout receipt, probe Absent, successful Login B, probe B, releases one duplicate old clear, waits for that effect's recorded completion, then probes Absent (I4); `CTRL-N3-EARLY-PUBLISH` starts with Login A0, receives current refresh success A1, captures actual UI version A1 while independent storage remains A0 at an evaluator barrier after publication/before failed replacement, then releases it and collects terminal failure/probe/end marker (I6); `CTRL-N4-FALSE-LOGOUT` ends immediately after failed-clear injection, returned Logout receipt and independent store probe (I5/I8), with no RetryCleanup step. Thus N2 never blocks Login B with uncleared A credentials, and N4 never depends on entering FaultLocked after its forged Completed status. Model/checker/native controls are separately labeled. Every control requires all declared receipts/probes/end markers; build failure or incomplete control is not successful detection.

Control trace schema can represent a declared detached effect with `effectId` and `originCommandRef` naming its prior Logout even after that command returned. This is structurally valid evidence of a semantic ordering violation, not permission for normal code to detach effects. CTRL-N2 declares that exact effect inventory; a missing/extra effect remains invalid. Control-specific barriers permit independent probe/UI capture only while store I/O is paused or finished. Completeness covers actions/receipts/effects/probes; the checker then evaluates their ordering and values against I1–I9.

## 9. Evaluation protocol and CI

Complete evaluator, workload, server contract, unsafe fixture, model controls, mutation anchors and runner interfaces first. Review and freeze their bytes plus baseline commit, spec hash, app-allowed paths, dependency locks, command templates and report schema using the existing change-protocol infrastructure. Add a narrowly validated `integration-comparator` protocol/report type there; keep all old protocols and negative controls. New evaluator tests must reject stale/missing artifacts, semantic verdict without actual mismatches, substituted runner commands and changed protected inputs.

Frozen stages: `integration-red` (unsafe fixture, required SEMANTIC_FAIL with named invariants), `candidate-ios`, `candidate-android`, `integration-controls`, `legacy-full`. Run and bind each result to manifest digest, candidate source digest, exact command, toolchain, app binary hash, inventory/runtime, scenario digest and fresh output artifacts. Aggregate PASS requires both native platforms, model/checker controls, native controls and legacy full gate. No SKIP_MUTATIONS for acceptance. A changed evaluator requires a new manifest and rerun of RED and affected candidate/control stages. Preserve superseded evidence.

The existing protocol's attempt/time budget is global to one manifest ledger and its unfinished-attempt lock requires sequential stages. Configure ten total attempts and 21600 total seconds, with the integration wrapper limiting each of the five stages to two attempts. Stage limits are integration-red 600s, candidate-ios 1200s, candidate-android 1200s, integration-controls 7200s, legacy-full 6600s. The 1200s value is the **whole platform stage**, including build/launch/all scenarios/export/check, never a per-scenario allowance. Controller waits are bounded by the remaining stage budget; native HTTP deadlines remain distinct. Retries consume the same global budget and are not guaranteed to fit; exhaustion is NOT_RUN, never PASS. Independent CI platform checkouts can run concurrently with separate ledgers; aggregation checks the same reviewed protected/source digests and required stage membership. Enumerate candidate source directories/files narrowly: a broad `apps/` allowlist overlapping protected harness files is invalid under the existing protocol.

Keep `.github/workflows/verify.yml` and `scripts/verify.sh` behavior intact. Add `scripts/integration-verify.sh` and a separate `.github/workflows/integration.yml` with a Python/model job, macOS iOS job and Linux Android job. Both app jobs start their own server and upload raw logs/results on failure. Proposed CI pin: iOS macOS-15/Xcode 16.2/iOS 18.2 Simulator; Android Ubuntu 24.04/JDK 17.0.13+11/API 35 Google APIs x86_64 emulator; Python 3.12.8. Runner image is still mutable: preflight inventory must select the requested runtime or produce infrastructure failure, never silently substitute another. Record actions' resolved SHAs and lock them during setup. An unavailable historical hosted runtime requires a reviewed app-CI pin change; it must not alter the old core CI pin silently.

Local Xcode 27.1 and installed iOS 17.0/17.5/18.6/26.5/27.0/27.1 runtimes were inventoried by the parent in this design session; local success on them would be a distinct toolchain record from CI. Select a dedicated simulator UUID from inventory or create a dedicated temporary simulator. Do not operate on an already booted user device. Android uses an owned temporary AVD under attempt-local `ANDROID_AVD_HOME`: API 35 Google APIs arm64-v8a on local Apple Silicon, API 35 Google APIs x86_64 on Linux CI. Record image revision, ABI, PID and serial; stop/delete only owned resources. Environment config passes `IOS_SIMULATOR_UDID` and `ANDROID_SERIAL`; neither is a committed machine-specific constant.

iOS Simulator uses host `127.0.0.1:<boundPort>`. Android emulator uses `10.0.2.2:<boundPort>`; USB physical Android may use explicit `adb reverse` for that port and loopback. Physical iOS uses explicitly configured private LAN host and local-network permission. Debug iOS Info.plist enables local networking ATS exception and describes local-network access; if raw-IP HTTP requires a broader ATS allowance on the selected OS, restrict `NSAllowsArbitraryLoads` to Debug config and retain the app-level private-address allowlist. Android Debug network-security-config permits cleartext and the app's URL validator restricts destinations to the configured loopback/emulator/private-LAN IP; a runtime LAN IP cannot be inserted into a precompiled XML domain list. Release config denies cleartext and excludes scenario controls. No arbitrary response-provided hosts or redirects. This app is distributed only as local development builds. [Apple local networking key](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking).

Bundle/application IDs are `dev.nativecontract.demo.ios` and `dev.nativecontract.demo.android`. Simulator builds need no personal development team or shared Keychain group. Physical iOS runs supply the operator's team at execution; no certificate/team ID is committed. Android uses local debug signing only. App-internal hook/audit protocols and no-op implementations compile in all configurations; Debug barrier/replay/fault implementations are injected only by Debug composition. Release sources never refer to Debug-only concrete classes.

No simulator/emulator start, dependency installation, app build, test, commit or push was performed while writing this design. The companion plan lists future commands; they are not evidence of PASS.
