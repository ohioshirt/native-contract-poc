# Native trace identity and mutation-anchor rules

This document is evaluator input. `mutation_matrix.json` freezes the proposed candidate source files, function names, exact Swift/Kotlin snippets, replacements, control IDs, and expected invariant sets for N1–N4. The exact anchors and installer are reviewed and frozen before candidate implementation; Tasks 4/5 then implement those signatures after the formal freeze and bound integration-red gate. `mutations.py` validates one exact match per language against the completed candidate and writes a hash-bound copied-source patch without changing the candidate. The isolated N2/N4 helper sources and Kotlin compile-only fixture exist and compile, but copied-candidate linkage and mutant execution remain pending; no mutation build or candidate behavior is frozen by this checkpoint.

## Command and observation inventory

For each process, `commandInventory` is exactly the selected `launches[].commands` sequence, or the selected `variants[].commands` sequence, in the scenario inventory. A command not listed there is invalid evidence. Prefixes are allowed only while a run is incomplete; the checker then reports the missing suffix as INCONCLUSIVE. A complete run must contain every listed command and one receipt per command.

`Logout(failed)` in APP-10-RECOVER-OLD is a frozen test-action label for the ordinary native `Logout` command with the declared clear fault armed. The harness taps the Logout control and applies the real store-wrapper fault; the native `commandEnqueued` and `commandInventory` rows retain the canonical name `Logout`. The checker contains this one explicit inventory-label-to-native-command mapping, so the alias cannot change reducer or storage semantics.

Native `Observe` is a FIFO `AppCommand`: it receives a command ID and `CommandReceipt`, reads the current projection/store without mutation, and publishes no new UI revision. The finite model deliberately abstracts `Observe` projections as stuttering steps; this does not change the native command contract. Current frozen automated scenario/control inventories use independent probes and rendered-view observations rather than declaring `Observe` commands. A native harness may submit `Observe` only when the command is in its selected frozen inventory. If checker support later admits a declared `Observe`, its read-only receipt must inherit the prior published UI revision/acknowledgement without requiring a new `uiPublishAck`.

The host's frozen storage-step ID is a checkpoint name, not app input. `DebugScenarioControl.probeStore()` returns a redacted `ProbeResult` envelope with the active `processInstanceId` and a fresh, checked per-process `probeId`; the probe ID is never derived from the host step ID and is never reused. XCUITest accepts a probe only when its envelope belongs to the active process and its probe ID differs from the previously displayed and captured IDs. The host independently rejects a reused probe ID before publishing the checkpoint.

The iOS visible `last-command-id` is the last completed command ID, and `last-command-status` is that command's terminal receipt status; neither advances when a command is merely enqueued or remains queued. `last-enqueued-command-id` is the highest command ID actually enqueued and can be greater while the consumer is paused. Replay scheduling compares the observed enqueue label with the newly enqueued replay command; paused-queue checks compare the completed ID with the last receipt before the pause. `view-revision` is a process-local UI publication revision and is independent of command IDs. The frozen session-state labels consumed by the controller are `Booting`, `Signed out`, `Signing out`, `Cleanup failed`/`Fault locked`, `Signed in …demo-A`/`Signed in …demo-B`, and `Refreshing …demo-A`/`Refreshing …demo-B`.

`ControlSnapshot.lastProcessedCommandRef` is a coherent terminal-receipt high-water mark. It advances only after the command's required storage verification and UI acknowledgement, and after its actual `commandReceipt` audit line is synchronized. It remains at the prior completed reference while a command is executing or paused; `lastEnqueuedCommandRef` may advance independently. APP-11 waits once for the final queued reference and records only that actual receipt observation. It does not require a latest-value UI register to display intermediate references: the independent checker still requires every native command receipt, their FIFO order, and the separate final store/render observations.

Native command IDs, event sequence numbers, UI revisions, and launch ordinals are positive signed 64-bit values. Each process namespace starts its local counters at one. Each `(platform, base scenario, variant)` case receives a unique bounded `attemptId`; its process references and artifact folder cannot alias another variant launch. `case_attempt_id` derives that attempt label from the base attempt plus platform/scenario/variant identity, and `case_artifact_directory` uses a variant-scoped output directory. A non-variant case retains its base attempt ID. In APP-12, p1 and p2 have different `processInstanceId` values but the same scenario-scoped storage namespace and one case output root. The controller records launch, termination, force-stop, receipt, probe, checkpoint, and direct-hook acknowledgements separately from the native event stream.

The candidate-owned Debug audit recorder exports each process's native JSONL to `native-harness/<attemptId>/<scenarioId>/p<launchOrdinal>/native-events.jsonl`; its source path is allowed candidate input, while this path, schema, and ordering contract are frozen evaluator inputs. Each record is appended as one complete UTF-8 JSONL line and synchronized to storage before a Debug control snapshot, enqueue/issuance progress label, or status checkpoint that exposes that record advances. A terminal `commandReceipt` is synchronized before the receipt is returned or the terminal control high-water mark advances. `uiPublishAck` reports the actual main-thread assignment acknowledgement, so it is recorded after that assignment; independent rendered-view evidence is bound to that acknowledgement, rather than assuming the audit line precedes the first rendered frame. In particular, `slotIssued` is synchronized before the Expire receipt and `commandEnqueued` before the enqueue snapshot/label; the recorder cannot queue writes behind these observations. iOS uses `FileHandle.synchronize()` or an equivalent durability barrier; Android syncs the output file descriptor. The recorder emits no credential payloads. On iOS the file is under the app data container's `Documents/`; on Android it is under `noBackupFilesDir/`, which `run-as` addresses with the explicit relative prefix `no_backup/`. Android instrumentation evidence and screenshots are stored under the same `noBackupFilesDir` process directory; the controller reads file bytes with `adb exec-out run-as`, while directory listings use `adb shell run-as`. The Android candidate creates each `noBackupFilesDir/demo-session/test-<attemptId>/<scenarioId>/` directory before its first storage probe and retains that owned directory across Bootstrap, Logout, clear, and RetryCleanup; clearing removes only the owned credential file and AtomicFile sidecars, never the namespace directory. A missing `no_backup/demo-session/...` namespace is `Unknown`, not proof that credentials are Absent, and leaves the comparison INCONCLUSIVE. The host copies native events into the attempt's `<scenarioId>/p<launchOrdinal>/native.jsonl` artifact and independent UI/storage observations into `ui.jsonl`; it never copies credential-file bytes to disk. A release decision reads the live native JSONL and selects the unique unconsumed `slotIssued.wireTag` for the declared slot. An ambiguous current slot is invalid controller history, never a numeric-minimum fallback.

## Process end and hook snapshot ordering

Each process has an explicit Debug control state `Open → Closing → Ended(ack)`. Only the protected harness may initiate this transition, after all inventory commands have terminal receipts and all required independent probes, rendered-view captures, screenshots and control actions are complete. Android instrumentation calls `DebugScenarioControl.finishProcess(timeoutMillis)` directly from its worker thread. iOS XCUITest taps the Debug panel action `finish-process`, waits for the panel value `process-end-ack-json`, then emits controller status phase `processEndAcknowledged`. Both emit the existing final `phase=end` only after the acknowledgement and before test-runner teardown/export. Application lifecycle callbacks never create `processEnd`.

`finishProcess` uses the Debug control synchronization boundary, not the auth mailbox. It atomically closes command/control ingress, lets already-admitted auth work reach quiescence within the supplied timeout, and rejects with `processBusy` (or `timeout`) without writing an end row while a hook is paused, a command/store operation is active, or the deadline expires. Once quiescent, it cancels any still-running physical transport producer and waits for its cancellation fence. This permits APP-07 to end with its second held request outstanding after the final Refreshing/A observations: late network callbacks are ignored before reducer dispatch, receipt, store access, UI publication or audit append, so the state projection and store are unchanged. Process end is not an auth command, receives no command ID, does not clear the store, and does not mutate auth UI. APP-12 p1 retains its installed app and scenario storage namespace for p2.

After ingress is sealed, admitted work is quiescent, and physical producers are fenced, the recorder appends and synchronizes exactly one terminal native `processEnd` row. It seals the native event stream against later appends and caches `ProcessEndAck(processInstanceId, eventRef)` where `eventRef` names that actual row. Repeating `finishProcess` returns the same cached acknowledgement and writes no second row. The controller accepts the acknowledgement only after a bounded live-audit read finds exactly one matching `processEnd` as the final row for that process; the host `processEndAcknowledged` controller event carries that native reference. A missing marker or acknowledgement is INCONCLUSIVE; a mismatched/duplicate reference is INVALID_HISTORY/INFRA_FAILURE, and any native row after `processEnd` is INVALID_HISTORY. The controller exports the completed journal before its separate owned-process force-stop.

Each `HookObservation.armSequence` is the positive signed-64 `ControlAck.actionId` returned by that hook's `arm`; it does not allocate a second ID. It remains unchanged from `armed` through `arrived` and `released`; it never wraps. One hook point can be armed once per process. `ControlSnapshot.hooks` retains every armed hook, including released hooks, until process end and presents them in strictly increasing, duplicate-free `armSequence` order. The controller validates this order and uses the latest sequence rather than point-name or enum ordering when interpreting the snapshot.

Each native stage receives an explicit device ID and ownership evidence path. The controller matches iOS UUIDs case-insensitively against `simctl` inventory, then passes the canonical inventory UUID to Xcode. Android evidence binds the serial to the owned AVD name and `ANDROID_AVD_HOME`; `adb -s <serial> emu avd name` must report that name before build, install, or force-stop. Only a controller-created device can be changed by the stage.

Every native `uiPublishAck` belongs to the single currently executing command. It appears after that command starts and before its receipt. A rendered-view observation is separate evidence: it names the acknowledgement event and revision, phase, and account. Bind it by process/revision/phase/account; the visible last-command label may lag while a command is paused and is not rendered-view provenance. An acknowledgement alone never proves what the user saw.

For CTRL-N3, the renderedView artifact carries process, revision, phase and account; it does not claim that accessibility text independently reports credential version. The rendered version-A1 fact is proven by the unique `uiPublishAck.view.credentialVersion` event bound through the same process/revision/phase/account `eventRef`. The independent storage probe separately records A0. The checker compares that bound native publication with the verified store observation to establish I6.

## Refresh request identity

`slotId` is a frozen trace identity supplied by the selected scenario or control, such as `slot-A1` or `slot-A2`. It is evidence-only; it is not sent as an app launch parameter or used as managed authority. `ownerId` and `epochId` are also opaque process-local evidence identities. They may be compared for equality in one history, but must not be recreated from a numeric request ID.

For each issuance, the decimal wire request ID equals the managed `RequestTokenRefresh` effect's request ID. The `wireTag` is exactly `<processInstanceId>:refresh:<issuanceCommandId>`, and a matching `requestHeld` server event is required for that tag. A `transportReceived` event names the issued slot, its exact wire tag, outcome, and frozen `failureCode`; a server response for another tag cannot complete it. The numeric request ID may repeat under a new managed owner only when the captured owner differs and the oracle records `ForeignRequest` with no state/effect change.

The event array is serialized in increasing process-local sequence order. The independent checker rejects reordered event records even when their sequence values could be sorted after the fact. Controller and server streams are separately contiguous and ordered by their own sequence fields.

## Barrier and storage-control provenance

An armed hook, arrival, and release are distinct native `hookEvent` rows sharing one `actionId`, point, and target. The controller records the corresponding hook acknowledgement and native event reference. The control release channel bypasses the authentication mailbox; it never relies on the paused consumer to process its own release.

Native store mutations that happen because of a direct hook release record the returned `ControlAck.actionId` as `releaseActionId`. The controller's `hookReleased.eventRef` must point to that process's actual released `hookEvent`; the checker joins the mutation to the native `actionId` through this reference. Controller sequence numbers are host-side ordering evidence only and are never written into native events. Restart `Bootstrap` clears and detached `DeferredLogoutClear` mutations must carry this native action link.

A declared detached storage effect has one exact `effectId`, an `originCommandRef` naming the earlier Logout command, one mutation and one matching readback. It does not borrow a refresh slot identity. Any undeclared, missing, duplicate, or differently originated effect makes the control history invalid or incomplete before invariant checking.

For CTRL-N2, the frozen action list releases `beforeDeferredControlClear` and then waits for the exact `late-clear-1` effect. The test runner asks the host for an effect-completion checkpoint; the host publishes it only after the live native audit stream contains that effect's mutation and readback. The resulting `detachedEffectAwaited` controller event carries both native event references and the Logout origin reference. The checker requires the acknowledgement after hook release and before the final physical probe, so a final probe cannot race the detached clear.

For `beforeDeferredControlClear`, the frozen `target: nextCommand` means the first detached clear continuation spawned by this process's Logout command. It does not refer to the next FIFO `AppCommand` dequeue: the later Login(B) command may be admitted and completed while that detached continuation is paused. Arrival is recorded from the detached effect's own native `hookEvent`; the effect keeps its original Logout command reference through release, mutation, readback and host acknowledgement.

`storeFault` describes a failed operation around the real store wrapper. Its `observation` is the wrapper's read result. `storeMutation` and `storeReadback` record actual operations and verification. A fault injection does not alter storage directly, and a failed candidate readback cannot be substituted for the later independent host/device probe.

## Hash and path conventions

`buildHash` is the lowercase ASCII form `sha256:` followed by exactly 64 lowercase hexadecimal digits. Exported artifact paths are relative to the attempt and process namespace; absolute paths, parent traversal, duplicate paths, stale files, and cross-process overwrites are invalid. Trace `platform` and build identity must agree with the platform result that owns the trace.

The frozen stage report lists one `traceBindings` entry per expected platform/scenario/variant tuple. A non-variant scenario uses `variantId: null`; a variant-bearing scenario has one entry for every frozen variant. Each entry's `buildHash` must equal its owning `platformResults[].buildHash`. A complete PASS or SEMANTIC_FAIL report cannot omit a variant binding, and the trusted stage runner derives the entries from the selected native histories rather than from the scenario list alone.

The anchor matrix is checked against the complete `control-scenarios.json` witness inventory during protocol configuration. N2 is anchored in the Logout caller (`handleLogout`), where its ordinary call to `clearThenPublishSignedOut` is replaced; the helper definition itself is not the mutation target. N3 compares the declared source lines with leading block indentation normalized while preserving their exact statement text and order.

`integration.mutation_installation` is the frozen copy/patch/install boundary. It asks `mutations.apply_mutation` to validate both Swift and Kotlin anchors against the original candidate, copies only the platform project and its local library dependencies into a fresh disjoint workspace, installs only the selected platform's patched source, and hashes the resulting workspace source tree. For N2/N4, Swift helper source is appended to the patched `SessionCoordinator.swift` followed by an isolated protocol-conformance extension. Kotlin helper source is installed under `app/src/debug/java/nativecontract/demo/mutation/`; the copied coordinator receives the helper imports and interface conformance. The normal candidate project and release source lists do not include these helper types. Any missing/duplicate caller anchor, helper input, or host adapter method is an infrastructure/build failure before a control can be marked detected.

Task 4/5 coordinator implementations must define these adapter methods exactly once in their source file, with the signatures required by the protected helper protocols. The ordinary auth path must not call them; only the copied mutant's injected conformance exposes them to the helper.

The copied build record binds the exact matrix/patch manifest, original and changed source hashes, helper hash and install destination, whole copied-source digest, build/test artifact hashes, and the actual app build hash. N1's two controls share its single N1 build; N2/N3/N4 each use their own build. Every trace binding records its own build hash. The protocol's control report keeps per-control build hashes and does not substitute a platform-wide or baseline hash.

Native execution scope is explicit. Omitted `NATIVE_CONTRACT_VALIDATION_SCOPE` means `ci`, and CI accepts only Xcode 16.2/iOS 18.2 or Android API35 x86_64 on the pinned runners. A developer who runs the same frozen comparator locally may set `NATIVE_CONTRACT_VALIDATION_SCOPE=local-observed`; the controller then requires the exact recorded local tuple and owned evidence hashes in `toolchain.json` (Xcode 27.1/iOS 18.6 build 22G86, Android API35 arm64-v8a image revision 9.0.0). The native platform result records `validationScope`; `verification.change_protocol` classifies a local-only native attempt as `INCONCLUSIVE`, and the final portable CI aggregator accepts only `ci`. Local evidence can therefore exercise the same commands, harness, independent probes, and checker while staying outside CI acceptance. The recorded local devices are inventory evidence only; their prior readiness checks did not run native app scenarios.

The N2 helper must perform normal verified Logout first, then schedule the declared detached effect with the old Logout `originCommandRef`, pause at `beforeDeferredControlClear`, and perform/record a real second clear after controller release. N4 injects `clearAfterBeforeVerify`: the wrapper physically applies the clear, then the candidate's readback is `Unknown`. The unsafe helper publishes SignedOut and forges a Completed receipt despite that unverified readback; the independent physical probe is therefore expected to be `Absent`, not a surviving credential. I5/I8 is the false-success receipt after failed verification. Helper fixture compilation does not prove candidate linkage or control detection. Before freeze, validate the exact matrix snippets, protected helper interfaces, installer and typed compile fixtures. Candidate anchors and adapters are implemented after formal freeze and bound semantic RED; before a control is `DETECTED`, its copied mutant app must then build, install, emit a complete history, and replay against the independent checker.
